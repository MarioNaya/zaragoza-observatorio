1. Flujo de datos

Nunca se hace proxy de la API municipal: todo se ingesta a tablas propias por jobs programados y se sirve desde ahí. El módulo ingestion no conoce ningún dominio; cada dominio traduce el JSON municipal en su adaptador anti-corrupción y escribe solo en sus tablas.

  1. El scheduler dispara un job para un DatasetRef.
  2. ingestion consulta la fuente con la estrategia incremental de esa fuente: FIQL por fecha en quejas, after en OCDS, recarga completa en juntas. If-Modified-Since no sirve: la API no lo honra (S0.5).
  3. Pagina con rows/start o por ventanas, aplica retry y circuit breaker, y entrega los payloads crudos al adaptador del módulo de dominio.
  4. El adaptador traduce y persiste con upsert idempotente por identificador de origen; reejecutar un job nunca duplica datos.
  5. Se registra el IngestionRun (inicio, fin, registros, estado, error) y se publica DatasetIngested a través del registro de eventos de Modulith.
  6. catalog recibe todos los DatasetIngested y actualiza la frescura observada de cada dataset.

3. Dentro de un módulo

Arquitectura hexagonal estricta, con catalog como ejemplo. El dominio define entidades y puertos y no importa Spring, JPA ni nada de infrastructure; los adaptadores implementan los puertos. Si el JSON municipal cambia, cambia solo el adaptador anti-corrupción.

  • Trazabilidad: cada registro conserva sourceDataset e ingestedAt; la API los devuelve siempre.
  • Sin conclusiones: ninguna etiqueta interpretativa ni indicador compuesto sin ADR; los umbrales de frescura son configurables y visibles.
  • Sesgos explícitos: toda agregación territorial devuelve el denominador de población, el número de incidencias sin asignar y caveats.
  • El backend decide qué datos y en qué orden; el frontend decide cómo se ven.
