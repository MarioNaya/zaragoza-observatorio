# CLAUDE.md — Observatorio de Datos Abiertos de Zaragoza

La especificación viva del proyecto es `SPEC.md` (ADR-000). Las decisiones de arquitectura están en `docs/decisions/`. Los hechos verificados sobre la API municipal están en `docs/spikes/`: **son la única fuente válida de endpoints, campos y formatos**; nada se escribe de memoria. **Al empezar una sesión, leer `docs/ESTADO.md`** (qué está hecho, qué toca ahora, cómo arrancar). Los diagramas de arquitectura están en `docs/arquitectura.md`.

## Reglas de trabajo (copia de SPEC.md §8)

1. **No inventar endpoints, campos ni formatos de la API municipal.** Si no está confirmado en `SPEC.md` o en `docs/spikes/`, se consulta con una petición real o se pregunta. Los campos se documentan con ejemplos de respuesta reales.
2. **Spikes antes de código de producción** para cualquier fuente nueva. Un spike es un script o test exploratorio más un informe en `docs/spikes/`.
3. **Respetar las fronteras de módulo.** Cada cambio debe pasar `ApplicationModules.verify()`. No se accede a tablas ni a clases internas de otro módulo. En particular: `workspace` nunca depende de un módulo de dominio; `territory` nunca tiene tablas propias.
4. **Hexagonal estricta**: el paquete `domain` no importa Spring, JPA ni nada de `infrastructure`. Los puertos son interfaces del dominio; los adaptadores viven en `infrastructure`.
5. **Idempotencia en toda ingesta.** Reejecutar un job no duplica datos.
6. **Nada de conclusiones en el código.** No se introducen etiquetas interpretativas ("degradado", "sospechoso", "anómalo") ni indicadores compuestos sin una decisión explícita documentada en `docs/decisions/` (formato ADR). **Limita la voz del producto, no la inferencia del usuario**: dar cruces, denominadores y series para que saque sus propias conclusiones es el objetivo (SPEC.md §1.1), no una excepción; no invocar esta regla para recortar capacidad de análisis.
7. **Toda agregación territorial expone denominador y caveats.**
8. **El backend ordena, filtra, pagina y agrega; el frontend pinta.** Ningún endpoint devuelve listas sin criterio de ordenación explícito.
9. **No se crea un módulo por dataset.** Una fuente nueva se asigna a un bounded context existente salvo decisión documentada en ADR.
10. **Tests antes de considerar algo terminado.** Sin Testcontainers en verde, no está hecho.
11. **Decisiones de arquitectura como ADR** en `docs/decisions/`, numeradas. `SPEC.md` es la ADR-000.
12. **Idioma**: código e identificadores en inglés; documentación, ADRs y textos de usuario en español.
13. **Commits pequeños y descriptivos**; una funcionalidad por rama.
14. **Preguntar antes de asumir** cuando una decisión no esté cubierta aquí y afecte a modelo de datos, fronteras de módulo, superficie de API o datos personales.
15. **Scaffolding y dependencias a través de las herramientas de cada ecosistema, nunca de memoria.** El objetivo es que ninguna coordenada, nombre de paquete ni versión se escriba recordada: siempre resuelta por la herramienta o verificada contra el repositorio oficial.
    - **Maven**: el proyecto se genera con Spring Initializr (CLI `spring init` o `curl` a `start.spring.io`) declarando ahí todas las dependencias iniciales; se usa el wrapper `./mvnw` generado, nunca un `mvn` global. Las dependencias posteriores se añaden al `pom.xml` **sin `<version>` explícita**, delegando en el BOM del parent de Spring Boot y en el BOM de Spring Modulith. Solo se escribe una versión cuando ningún BOM la gestiona, y en ese caso se verifica antes contra Maven Central (búsqueda o `./mvnw dependency:resolve`); no se escribe de memoria.
    - **Node / Angular**: el proyecto se crea con `ng new`; los paquetes se añaden con `npm install <paquete>` (o `ng add`), nunca editando `package.json` a mano. El lockfile se versiona y se instala con `npm ci`.
    - **Verificación inmediata**: tras cualquier cambio de dependencias o de scaffolding, compilación y tests en el mismo paso (`./mvnw verify`, `npm ci && npm run build`). No se encadena un segundo cambio sobre uno que no compila.
    - Ficheros de configuración de herramientas (`pom.xml`, `package.json`, `angular.json`) se editan a mano solo para lo que la herramienta no cubre (plugins de build, perfiles, scripts), y siempre seguido de la verificación anterior.

## Reglas adicionales (ADR-001 a ADR-018, más las fuentes que entran sin ADR con su spike)

16. **Spikes = tests JUnit etiquetados.** Cada spike es una clase `S<fase><n>NombreSpike` (`S04GeoSpike`, `S12ApiInventorySpike`, `S21TerritoryResolutionSpike`) con `@Tag("spike")` en `src/test/java/es/zaragoza/observatory/spikes/`, excluida del build por defecto y ejecutada con `.\mvnw.cmd test -Pspikes`. Guarda respuestas crudas en `src/test/resources/fixtures/zaragoza/` y su informe va en `docs/spikes/`.
17. **Stack real**: Spring Boot 4.1.x (starters modulares: `spring-boot-starter-webmvc`, `-restclient`, `-flyway`…), Spring Modulith 2.1.x vía BOM, Java 21, Jackson 3 (`tools.jackson`). Cuando dudes de un paquete o artefacto, mira `pom.xml` y `.\mvnw.cmd dependency:tree`, no la memoria.
18. **API municipal, reglas verificadas (S0.5)**: URL siempre con extensión `.json`/`.geojson` y `srsname=wgs84`; `rows` tope 500 en la sede, **1.000 en Open311** (S2.3 corrige el «sin tope» que decía esta regla; en OCDS sigue sin medirse tope); `start` ignorado en OCDS; `If-Modified-Since` nunca se honra y solo Open311 honra `ETag`; `Last-Modified` llega con zona `CET/CEST` (no RFC 1123); fechas sin zona son hora local, presupuesto usa `yyyyMMdd`; FIQL (`q`) tiene lista blanca de campos por endpoint. Los detalles y excepciones están en `docs/spikes/`.
19. **Unidad territorial = junta municipal o vecinal (29)**, opcionalmente sección censal (491). No existen barrios como dato abierto (S0.4). El gasto público (OCDS, presupuesto, subvenciones) **no tiene dimensión territorial** (S0.2, S0.6): no se inventa geocodificación.
20. **El contexto de gasto se llama `spending`** (ADR-003): OCDS + presupuesto + subvenciones, sin entidades territoriales; `spending` no depende de `geo` y `territory` no depende de `spending`. Licencias, locales y obras en vía pública quedan fuera (candidato posterior `urban-activity`, con ADR propia).
21. **Infraestructura de fase 1 (ADR-004)**: el registro de eventos de Modulith va sobre JDBC y su tabla la crea Flyway (V002); `spring.jpa.hibernate.ddl-auto=validate`, así que **toda entidad JPA nueva necesita su migración** y declara `columnDefinition` (`text`, `timestamptz`, `timestamp`, `boolean`) para que la validación case con PostgreSQL. Resilience4j se usa de forma programática dentro de `ZaragozaHttpClient` (retry solo en 5xx/timeout/E-S/HTML, circuit breaker por dataset, semáforo de 4); timeouts y redirecciones por `spring.http.clients.*`. Cada fuente nueva se declara como bean `IngestionJob` en el módulo dueño (descriptor + `interval()` + `handle(RawPage)`) y su adaptador se prueba con `MockRestServiceServer` sobre fixtures reales grabados con cabeceras. El contrato de la API propia lo genera springdoc (`/v3/api-docs`). Al cerrar un run se publica `DatasetIngested`; los listeners de otros módulos son `@ApplicationModuleListener`.
22. **Ningún dato personal de terceros entra en el repositorio.** El ayuntamiento publica el texto libre de quejas y sugerencias sin anonimizar (nombres y DNI dentro de `title`/`description`, comprobado el 2026-09-06). Los fixtures de fuentes con texto ciudadano se guardan con `SpikeFixtures.saveRedacted(...)` (campos sustituidos por un marcador); las cabeceras grabadas nunca incluyen `Set-Cookie`; antes de subir a GitHub se pasa `git grep` a los fixtures buscando DNI (`\b[0-9]{8}[A-Z]\b`), correos y firmas («atentamente»). El historial se limpió con `git filter-repo` el 2026-09-06; no volver a introducir esos datos. En el producto (fase 2), el texto libre de las quejas no se republica tal cual (SPEC.md §4.6, §9).
23. **Eje observado de la frescura (ADR-005, S1.1 en `docs/spikes/S1.1-frescura-observada.md`).** Solo cuatro métodos de observación (`FILE_HEADERS` por `HEAD`, `API_MAX_DATE` por `rows=1&sort=<campo> desc`, `API_COUNT`, `WFS_HITS` por `resultType=hits`) y una lista blanca cerrada de campos de fecha (`ObservationUrls.DATE_FIELDS`); las reglas de URL están en `ObservationUrls` y se prueban con los fixtures de `catalog/observation/`. Ningún método se añade ni se cambia un campo de la lista sin petición real y fixture. No existe categoría observada ni cruce declarado/observado: se publican medidas con su método y sus errores; una categoría exige una serie de instantáneas y una ADR (regla 6). El `RestClient` es un bean único de la aplicación (`HttpClientConfiguration`, como el `Clock`): timeouts y redirecciones por `spring.http.clients.*`, `User-Agent` por `zaragoza.http.user-agent`; ningún módulo construye otro cliente ni escribe cabeceras de identificación a mano (con dos clientes el `MockRestServiceServer` autoconfigurado de los tests deja de funcionar).
24. **Inventario de endpoints (ADR-006, S1.2 en `docs/spikes/S1.2-inventario-api.md`).** El Swagger 2.0 de la API (`sede/servicio/catalogo/api.json`) se ingiere como documento único (`SourceDescriptor.document`, `ResponseShape.DOCUMENT`: sin `rows` ni `start`; la fuente no publica `Last-Modified` ni `ETag` y responde 400 a `HEAD`) y se sincroniza entero en `catalog_api_endpoint` (`tag + method + path`, con `firstSeenAt`/`lastSeenAt`). El cruce con las fichas es por `apiTag` al leer, sin tabla de enlace. Del Swagger, la observación solo usa el `<downloadURL>/list` documentado en el tag de la ficha (`ObservationUrls.documentedListUrl`, comparación sin tildes): el «primer path del tag» no es unívoco cuando el tag agrupa varios recursos, y no se añade ningún otro path sin petición real y fixture.
25. **Federación en datos.gob.es (ADR-007, S1.3 en `docs/spikes/S1.3-federacion.md`).** Fuente `datos-gob-es:publisher/L01502973`: paginación `Pagination.pages(200, "_page", "_pageSize")` (tope 200 validado; `next` pierde el tamaño y no se sigue) y forma `RESULT_ITEMS`; sin `Last-Modified` ni `ETag`. Tabla propia `catalog_federated_dataset` con upsert por página y baja de lo no visto al completar la ingesta (listener de `DatasetIngested`); `federated` se resuelve al leer por `sourceId`. **El listado `catalogo.json` no es todo el catálogo**: omite las partes de series y colecciones (108 federadas, `datasetRelacionado IS_PART_OF` en el detalle); no se ingieren hasta que haya spike y ADR (SPEC.md §9).
26. **Despliegue (ADR-008, procedimiento en `docs/despliegue.md`).** La imagen es el `Dockerfile` multietapa de la raíz: se compila con el wrapper del proyecto y se ejecuta sobre JRE 21 como usuario no root, con extracción por capas de Boot (`jarmode=tools`). **Los tests no corren en el builder** (Testcontainers necesita Docker): la puerta sigue siendo `.\mvnw.cmd verify`, se compila con `-Dmaven.test.skip=true` y `src/test/` está fuera del contexto (`.dockerignore`), lo que además impide que un fixture viaje a la imagen (regla 22). La base de datos usa la **imagen `postgis/postgis:17-3.5`**, la misma que dev y Testcontainers; un Postgres sin PostGIS no arranca (`V001`). Se declara como **`service` con `image(...)` y volumen explícito, nunca con el ayudante `database(...)`**: con imagen propia, `database()` provoca un bucle de borrar y recrear (ADR-008 §8). Y su `PGDATA` va a un directorio propio, porque Railway inicializa el volumen con Postgres 18 y la imagen 17 no arranca sobre ese clúster. La conexión se configura con `PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD`, **sin valor por defecto**: si falta una, la aplicación falla al arrancar en vez de caer a un valor de dev. En `prod` el actuator expone solo `health` e `info` (**`/actuator/modulith` no se expone**) y springdoc sí (el contrato es producto, SPEC.md §4.9). **Una sola réplica**: sin ShedLock, dos instancias duplicarían el planificador (ADR-004). La infraestructura se declara en **`.railway/railway.ts`** (Infrastructure as Code; `railway.json` está deprecado y no se usa): `railway config plan` antes de `railway config apply`, y **en IaC lo que no está en el fichero se borra**, así que todo servicio nuevo se añade ahí y no por el panel. Ese fichero **no lleva secretos** —la contraseña la generó Railway, figura como `preserve()` y la app la recibe con `ref(postgis, "PGPASSWORD")`—; nunca ejecutar `railway config pull --include-variables`, que los descifra y los escribe. Antes de publicar, probar la imagen real con `docker compose -f compose.prod.yaml up --build -d` (proyecto y volumen propios: no toca los datos de desarrollo).
27. **El coste del despliegue se paga en RAM residente (ADR-009), no en peticiones.** Railway cobra 10 $/GB/mes de memoria y **nada por petición**; con poco tráfico, la factura es la memoria ocupada 24 h. Por eso `JAVA_TOOL_OPTIONS` fija topes **explícitos** (`-Xmx256m`, metaspace, `-Xss512k`, `UseSerialGC`, `TieredStopAtLevel=1`, `ReservedCodeCacheSize=64m`) y no un porcentaje: Railway anuncia el límite del plan (8 GB), así que un `MaxRAMPercentage` deja crecer el heap a varios GB y el proceso se estabiliza en ~690 MB en vez de ~370 MB. **Cualquier cambio en esas banderas se mide antes** con `compose.prod.yaml` y `docker stats` sobre una ingesta completa más un lote de observación, y después en `railway metrics`. El modo **Serverless no se usa**: el planificador es el producto, y un servicio dormido no ingiere. `TieredStopAtLevel=1` es lo primero que hay que revisar si aparece trabajo de cálculo intensivo (agregaciones de la fase 4).

28. **Las copias del volumen no se declaran en la IaC (ADR-010, comandos en `docs/despliegue.md` §7).** Railway acepta `backupSchedules` en el grafo y `railway config plan` lo muestra, pero **`railway config apply` responde `changes: []` y no aplica nada, ni lee el estado real**: la línea dejaría el `plan` sucio para siempre y este repositorio depende de que un `plan` limpio signifique «sin deriva». Se gobiernan por la API pública (`railway api`, mutación `volumeInstanceBackupScheduleUpdate`, consulta `volumeInstanceBackupScheduleList`) sobre el **id de la instancia** del volumen, no el del volumen. Exigen **plan Pro** (en Hobby la mutación devuelve `Not Authorized`), y por eso el suelo de coste es 20 $/mes con 20 $ de uso incluido, de la cuenta y no del proyecto. Activos `DAILY` (6 días), `WEEKLY` (27) y `MONTHLY` (89). **El PITR no es alternativa**: solo corre sobre las imágenes de base de datos de Railway, y la nuestra es PostGIS. Una política declarada no es una copia: se comprueba con `volumeInstanceBackupList`, y una copia manual (`volumeInstanceBackupCreate`) prueba el mecanismo en segundos sin redesplegar.

29. **La junta se resuelve por geometría, nunca preguntando a la API (ADR-011, S2.1 en `docs/spikes/S2.1-resolucion-territorial.md`).** Lo que S0.4 y S0.6 daban por sabido era falso: `portalero/v2` es un **buscador** de direcciones, no un resolutor —sin `totalCount` (siempre `-1`), la `junta` llega sin `id` y con la tilde rota, el FIQL `q=junta.id==N` no filtra por junta y una calle inexistente devuelve **otra calle** con ese número—; acierta la junta en el 89,5 % **sin que la respuesta permita distinguir el acierto del fallo**. Y `point`+`distance` no filtra por proximidad en ninguno de los dos recursos que lo documentan (`registro-licencia/portal` responde 400 con un error de Hibernate). La asignación territorial se hace en casa con `ST_Contains` sobre los 29 polígonos de `distrito.json?srsname=wgs84` (99,69 % de acuerdo con la junta oficial de `locales-vacios`), y **sin punto no hay junta**: el registro queda sin asignar y se cuenta como tal (regla 7), nunca se geocodifica por dirección para rellenar el hueco. Toda fuente territorial guarda dos campos: `districtId` (resuelto) y `districtDeclared` (lo que diga el origen, como contraste, nunca como sustituto). `District` lleva las dos numeraciones, `id` (= `distrito.id` = `iddatosab`) y `padronId` (= `idpadron`), publicadas juntas en `distrito/{id}.indicadores`; el padrón por junta tiene **2020, 2021, 2022 y 2024**, sin 2023: la serie no es continua y toda normalización declara el año que usa. Los 29 polígonos **no son una partición** (se solapan en el entorno de Juslibol): la ambigüedad se registra, no se resuelve en silencio.

30. **El texto libre de las quejas no se pide (ADR-012, S2.2 en `docs/spikes/S2.2-quejas-ingesta.md`).** El parámetro `fl` de la sede recorta de verdad la respuesta, así que la ingesta de `citizen` manda una proyección fija de **ocho campos** (`service_request_id`, `status`, `service_code`, `service_name`, `requested_datetime`, `updated_datetime`, `geometry`, `district`) y `title`, `description` y `service_notice` **no se descargan, no llegan a `raw_payload` y no tienen columna**; `address_string` tampoco se pide, porque ADR-011 §2 prohíbe geocodificar por dirección y no tiene uso. La redacción por patrones quedó descartada con datos: 2 DNI en 7.000 registros frente a 3.353 (47,9 %) con fórmula de firma, que ninguna expresión regular reconoce. La garantía es doble y está probada (la proyección hace fallar el arranque si alguien añade un campo prohibido; el traductor ignora esos campos aunque lleguen). Otras reglas verificadas de esta fuente: el listado tiene **89.432 registros** y es un **subconjunto** (`statistics` cuenta ~40.000 cerradas/año); el **orden por defecto no es fiable** y toda petición manda `sort` explícito; **el barrido completo solo es exacto por `requested_datetime`** —por `updated_datetime` las mismas 89.432 filas dan solo 80.628 ids distintos, porque las quejas cerradas por lotes empatan en fecha y entre filas empatadas el orden no es estable entre páginas—, así que la carga del histórico la hace únicamente el job de altas y el de cierres nunca barre el listado entero; **que dos páginas consecutivas no solapen no prueba que un barrido esté completo**: se cuenta por identificadores distintos, no por filas; `updated_datetime` **sí** admite FIQL y `sort`, y es el eje por el que se capturan los cierres; la cobertura de punto del histórico va del **16 % al 45 %** según el año, así que las series por junta y año no son comparables sin publicar la cobertura al lado. Los cuatro sinónimos de nombre de junta que ADR-011 §5 pedía documentar están en `DistrictNames` con su evidencia: `DISTRITO SUR`→30, `SAN JUAN DE MOZARRIFAR`→25, `TORRECILLA`→26 y `CASCO HISTÓRICO` con un U+0093 intercalado→3.

31. **Las fichas que dejan de aparecer en el catálogo se marcan, no se borran (ADR-013).** El listado municipal encoge (436 → 434 el 2026-09-09: «Paradas Bus» 4008 y «Paradas Tranvía» 4010, cuyo `catalogo/{id}.json` responde 404) y `RegisterDatasets` solo hace upsert. `catalog_dataset` lleva `delisted_at` (V010): el inicio de la primera ingesta completa en la que la ficha faltó, `null` si apareció en la última. Lo pone y lo quita el listener de `DatasetIngested` en cada ingesta del catálogo, con la frontera del `startedAt` de **esa** ejecución (no la última correcta) y en las dos direcciones: si la ficha vuelve, la marca desaparece. **La ficha no se borra nunca** —su histórico de frescura es el producto, al revés que en la federación, donde sí se purga (S1.3)—, se sigue observando y sigue tomando instantánea diaria. La API lo publica como hecho fechado: `listed`/`delistedAt` en listado y detalle, filtro `listed` y recuento `notListed` en `summary`, donde `datasets` **sigue contando todas** las fichas ingeridas. El `caveats` dice que es una afirmación sobre el listado y no sobre el dato ni sobre lo que hizo el publicador (regla 6). Dos salvaguardas contra un marcado masivo espurio: un listado sin `result` hace **fallar** la ingesta (el traductor lanza) y no publica evento, y el listener no marca nada si la ejecución trajo 0 registros.

32. **Open311 no se ingiere: publica un subconjunto estricto del listado de sede (ADR-014, S2.3 en `docs/spikes/S2.3-contraste-open311.md`).** El contraste por conjuntos de identificadores en cuatro meses de 2017, 2025 y 2026 y en **2025 entero** (11.895 registros) da **cero** registros que Open311 publique y la sede omita; lo que falta en Open311 son las `INTERNAL` (247 de 11.895 en 2025, `service_code` 2, sin documentar en `services.json`, 404 en su detalle) y cinco registros que además responden 400 en el detalle de la sede. Tampoco aporta territorio: cero quejas que sitúe y la sede no, y cero discrepancias de coordenada o de junta declarada en los 1.027 comunes de agosto de 2026. Por eso **el hueco entre los 89.432 registros del listado y las ~40.000 cerradas/año de `statistics.json` no es una diferencia entre las dos API**, y la duda sobre el criterio de publicación sigue abierta sin que otro endpoint pueda cerrarla. De Open311 se sigue usando solo `services.json` (taxonomía). Trampas medidas de esa API, para quien la toque: **la ventana se recorta a 3 meses desde `start_date` en silencio** (un año pedido devuelve un trimestre con aspecto de completo; sin fechas, los últimos 3 meses), `rows` topa en 1.000, `totalCount` vale siempre 0, `fl=…,lat,long` devuelve `lat` sin `long` y **`requested_datetime` lleva la hora local convertida dos veces y marcada con `Z`** (desfase del doble del huso frente a la sede), así que las dos fuentes solo se cruzan por identificador, nunca por fecha.


33. **El producto da columnas, no ajustes (ADR-015).** Dos cifras de `citizen` no se pueden leer tal cual, y ninguna de las dos se arregla decidiendo por el lector. **Los servicios `INTERNAL`** (`service_code` **2**, 2.449 de 89.432, no documentados en `services.json` y ausentes de Open311, S2.3) **siguen contando**, cada grupo publica cuántos son en `internal` y el parámetro `internal=include|exclude|only` deja que los quite quien lee; excluirlos en silencio sería decidir qué es una queja (regla 6). **Las series por junta y año** se publican como cruce, `by=district_year`: un grupo por junta y año con su total, sus cerradas, su `withPoint` y el padrón **de ese año** (`geo.populations()`), porque usar el año más reciente para toda la serie mezcla dos cosas distintas. **La cobertura de punto que sirve para comparar años va aparte, en `coverageByYear`**: dentro de un grupo por junta vale siempre 1 por construcción —sin punto no hay junta—, así que un 1,00 por grupo no dice nada y lo que hay que mirar es cuántas quejas de todo el año se pudieron situar. Los años sin padrón (todos menos 2020, 2021, 2022 y 2024) salen sin denominador: **el hueco se ve, no se interpola**. Y **nada se ajusta por cobertura**, aquí ni en ningún sitio: un ajuste supone que lo no geolocalizado se reparte como lo geolocalizado, y eso no está comprobado.

34. **La actividad urbana privada es el contexto `urban`, y no guarda una sola línea de texto libre (ADR-016, S2.4 en `docs/spikes/S2.4-registro-licencia.md`).** ADR-003 §6 lo dejaba previsto como `urban-activity` «con ADR propia»; se funda ahora con `registro-licencia` (42.342 locales, 69.631 licencias) y admite después `licencia-obra`, `locales-vacios` y `via-publica` **sin ADR nueva**, cada una con su spike. Reglas verificadas que este módulo no puede saltarse: **el barrido va siempre por `sort=id asc`** y la ventana incremental en `q=lastUpdated=ge=…`, porque por `lastUpdated` la paginación pierde 2.928 registros (22.044 locales comparten un mismo instante de carga); **se piden los registros completos, sin `fl`**, porque la proyección **vacía los objetos anidados** (una licencia proyectada llega sin año, sin expediente y sin tipo) y `removeproperties` se acepta sin aplicarse, que es el mismo patrón de `q=junta.id==N` (S2.1) y `status=rejected` (S2.2); la licencia se identifica por **`(local, año, expediente)`**, nunca por `orden`, que colisiona 950 veces. Aquí **el texto libre no se puede dejar de descargar**, al revés que en ADR-012, así que la garantía es triple y está probada: no hay columna, el traductor no lo lee y **la página cruda no se guarda** (`IngestionJob.keepsRawPayload()` a `false`; contiene 15 DNI con letra de control válida). `actividad` se descarta porque el **epígrafe IAE** dice lo mismo codificado y lo traen los 42.342 registros; `emplazamiento`, porque ADR-011 §2 prohíbe geocodificar por dirección. **Esta fuente no declara junta**: no se crea `districtDeclared` ni se fabrica cruzando `codPortal` contra el callejero, y la ausencia se dice en `caveats`. `estado` (0..3) y `zonaSaturada` se publican **como códigos** porque no hay taxonomía —los locales usan 17 zonas y la API publica 15—, y ninguna cifra se llama «locales abiertos»: es un registro de licencias concedidas. La API separa unidades: `/premises` cuenta locales y los ejes `licence_*` cuentan licencias, y cada respuesta lo declara en `unit`. El vocabulario de asignación territorial (`RESOLVED`/`AMBIGUOUS`/`OUTSIDE`/`NO_POINT`) vive ahora en **`geo.Assignment`**, no en `citizen`.

35. **La contratación OCDS se enumera con un interruptor, no con una fecha (ADR-017, S3.1 en `docs/spikes/S3.1-ocds-ingesta.md`).** El listado que documenta la API es un **subconjunto estricto**: publica 5.730 de los 8.001 procesos, y los 2.271 que esconde solo salen mandando `after`, que **no es una fecha** —por debajo de un umbral entre el 1 y el 2 de enero de 2017 no hace nada y por encima el valor da igual—; `before` sí filtra por fecha de publicación pero solo el conjunto base, y **ninguno de los dos sirve de marca de agua**. Por eso el censo va siempre con `after=2030-01-01T00:00:00Z` (`OcdsListing.AFTER_SWITCH`), en cada ingesta se comprueba que el listado documentado **sigue siendo subconjunto** del ampliado —si deja de serlo, se falla, no se adivina— y se publica `inDocumentedList` por proceso. **El listado solo trae `ocid` e `id`**: el detalle son 8.001 peticiones y no cabe en `handle(RawPage)`, así que lo lee un planificador propio del módulo por lotes (patrón de ADR-005) con **cadencia decreciente** (1, 2, 4… días con tope de 30 para los que no tienen release; 7 o 30 días de refresco para los publicados, porque la fuente no da `ETag` ni `Last-Modified`). **Un proceso sin release no es un error**: son el 29,7 % y los recientes; se guardan con su estado (`PENDING`/`PUBLISHED`/`EMPTY`/`ABSENT`) y se reintentan —un 200 no garantiza release (16 packages vacíos) y el 404 llega con un cuerpo que dice 400—. **`stage` solo donde el documento lo sostiene**: `COMMITTED` exige fecha de firma (3.410) y los 1.560 procesos cuyo contrato es una cáscara salen **sin etapa** (regla 6); `EXECUTED` no existe aquí (0 `planning`, 0 `implementation`) y el importe es licitado o adjudicado, **nunca pagado**, en dos columnas separadas. En datos personales el orden de magnitud es otro que en `citizen` y `urban` —0 DNI y 0 NIE válidos en 5.622 documentos—, así que **el texto libre sí se guarda** y la página cruda del listado también; lo que no se guarda nunca es `parties[].id`, que lleva el **NIF incrustado**: se descompone, el NIF de persona jurídica entra y de una **persona física no entra ni NIF ni nombre**, con la restricción `spending_award_party_no_natural_identity` imponiéndolo desde la base de datos. El recurso se publica como `/spending/processes`, no `contracts`.

36. **El presupuesto de gastos se enumera por instantáneas y se lee una sola vez (S3.2 en `docs/spikes/S3.2-presupuesto-ingesta.md`).** Es la **única fuente de gasto ejecutado** del producto —OCDS publica licitado y adjudicado, nunca pagado (regla 35)— y entra en `spending` sin ADR nueva, como preveían ADR-003 §2 y `docs/ESTADO.md` §4. El censo es `presupuesto/gasto-corriente/fecha.json`: 140 fechas de 2006-12-31 a 2026-08-31, una petición, `result` con **URL y no objetos**, e ignora `rows`. Cada instantánea es una foto **acumulada desde enero** del presupuesto entero (722 a 1.303 partidas, 154.508 filas en total), así que **sumar las doce fotos de un año cuenta el mismo euro doce veces**: la serie por año toma la última instantánea de cada ejercicio y cada grupo publica de qué foto sale. **Toda petición manda `sort=id asc`** (`BudgetListing`): el orden por defecto de este endpoint sirve **dos ordenaciones distintas a la misma URL** —cinco y cinco en diez peticiones seguidas—, peor que el de las quejas (regla 30) porque puede cambiar entre dos páginas del mismo barrido; con `sort=id asc` el barrido de las 140 no perdió ni repitió una fila. **Una instantánea publicada no se reescribe** (comprobado a cinco días con el fixture de S0.6), así que se lee una vez y se **congela** (`next_attempt_at` a `NULL`) y solo se relee la más reciente: el histórico entero son 396 peticiones y 2,3 minutos, y lo lee un planificador propio del módulo por lotes, como el detalle de OCDS. La clave es **`(fecha, concepto)`** —el `id` del origen es esa misma clave con la fecha pegada delante— y `concepto` lleva el ejercicio dentro: **ninguno de los 22.838 conceptos cruza de año**; el eje plurianual es `(órgano, programa, epígrafe)` y no se publica todavía. Los **ocho importes** cuadran al céntimo en tres identidades contables, y las cuatro que importan —crédito definitivo, comprometido, **obligación neta = gasto ejecutado** y pago neto— **no son intercambiables**: se publican las cuatro por separado y ninguna se llama «gasto» a secas (regla 33). **`gasto-corriente` no es solo gasto corriente**: trae inversiones reales (capítulo 6) y los capítulos financieros. El **programa no existe en 2010-2014** y llega incompleto en otros seis ejercicios (32.618 filas sin programa): el nulo es el dato y su grupo sale como tal. Los códigos antiguos llegan rellenos con espacios y solo se recortan. Los tres **resúmenes anuales no se ingieren**: cuadran al céntimo con las instantáneas y empiezan en 2015, cuando la serie propia llega a 2006. `ingreso-corriente` queda fuera: el contexto es gasto (ADR-003). En datos personales, **cero DNI, NIE, correos y teléfonos en las 154.508 filas**, pero **cuatro filas de 2006-2009 nombran a una persona física** («a la viuda de D. …»): el nombre de la partida se guarda —sin él es un importe sin concepto— salvo en las filas que casan la **lista cerrada** de `BudgetHeading`, que entran sin texto y con `heading_redacted`, con el recuento en `caveats` y el CHECK `spending_budget_line_redacted_has_no_text` imponiéndolo desde la base de datos. **Ampliar esa lista exige volver a medir.**

37. **Las subvenciones entran con el beneficiario contado y no nombrado (ADR-018, S3.3 en `docs/spikes/S3.3-subvenciones-ingesta.md`).** Es la tercera y última fuente de `spending` y la primera del proyecto en la que **el dato personal es el contenido**: una subvención sin beneficiario es un importe sin destinatario. Y la fuente **se contradice**: enmascara el NIF de la persona física (`***332**`), titula «Datos de caracter personal» a las 16.450 fichas que clasifica así —sin dirección, teléfono ni correo— y a la vez **publica el nombre y apellidos de 6.333 beneficiarios** en `adjudicatario.nombre` y **2.378 DNI y 381 NIE con letra de control válida dentro del `title`**. La respuesta es la quinta de la serie y combina dos figuras anteriores: **el nombre no se descarga** (proyección fija sin `adjudicatario`, que hace fallar el arranque si alguien lo añade, como ADR-012) y **el identificador del título se redacta por forma, no por validez**, con `title_redacted` y su recuento en `caveats`. Del beneficiario entra **siempre el seudónimo** que ya publica la fuente —permite contar cuánto recibe el mismo sin saber quién es— y el nombre y el NIF **solo si no es una persona física**, que se decide por la **unión** de las dos señales (clasificación del directorio o identificador enmascarado; discrepan en 70 beneficiarios). **Ningún dato de contacto entra**, de nadie. Dos CHECK lo imponen desde la base de datos (`spending_grant_beneficiary_no_natural_identity` y `spending_grant_title_has_no_identity`, el primero del proyecto con expresión regular). Reglas verificadas de esta fuente: **el censo completo es la versión vieja** (`ayuda-subvencion/resolucion`, 46.925 de 2013 a 2026) y `ayuda-subvencion-v2` es un **subconjunto estricto** que esconde 2013 y 2014 —de la v2 solo se usa el enlace con el beneficiario, que la v1 no publica—; **nunca se mandan `rows` y `page` juntos**, porque el desplazamiento lo calcula `pageSize` aunque el tamaño lo fije `rows` y las páginas se solapan en silencio; **`rows` topa en 500 y `pageSize` no topa en nada**; **`fl` recorta de verdad en la v1** pero **por subárbol y a dos niveles** (la salida es la **ruta con punto**, no documentada) y **sobre la v2 devuelve `{}`**; el orden por defecto **sí** es estable aquí, pero todo barrido manda `sort=id asc` igual; `q=id=gt=N` es la marca de agua de la ingesta diaria; y los cuatro recursos se ingieren **sin orden**, con el enlace guardado aunque su concesión no exista todavía. Ninguna cifra es dinero pagado: `granted` es lo acordado, y lo pagado sigue saliendo solo del presupuesto.

38. **El cruce territorial da columnas con su cobertura, no vistas ni cocientes (ADR-019).** Es la primera pieza de la fase 4 y va **antes** de la primera pantalla, como exigía SPEC.md §3. El módulo `territory` compone llamando a las superficies públicas de `geo`, `citizen` y `urban`: **ni tablas, ni caché, ni ingesta, y nadie depende de él** (regla 3). Por eso `citizen` y `urban` estrenan paquete raíz como API de módulo (`Citizen`, `Urban`), y lo que entra ahí es contrato. Dos recursos, `GET /api/v1/territory/districts` (matriz de 29 filas) y `/districts/{id}` (ficha con la serie de padrón entera). **El catálogo de medidas es cerrado** —`citizen.requests`, `urban.premises`, `urban.licences`— y crece añadiendo una entrada, nunca abriendo un parámetro: un `groupBy` libre obligaría a publicar el modelo interno de cada módulo. Son tres y de dos módulos porque **es lo que hay territorializable**; pedir `spending.*` responde **400 diciendo por qué**, no una columna de ceros. Reglas que no se saltan: **la suma de las 29 filas es `assigned`, no `total`** (medido en real: quejas 26.105 de 89.515, cobertura 29,2 %; locales 37.829 de 42.344, 89,4 %; licencias 63.093 de 69.633, **90,6 %**, que no es la de locales —por eso la cobertura de una columna de licencias se mide en licencias, con `licenceAssignmentCounts`, y no se reutiliza la de locales—); **la ventana se aplica sobre la fecha que cada medida declara** y en `urban` es el **alta del local**, no el año de licencia; **el denominador es otro catálogo cerrado** (`population|none`) y su año viaja en cada fila, sin caer nunca a otro año si el pedido no existe (con `populationYear=2023` salen **las 29 sin denominador**, que es el hueco de la serie a la vista); **no se divide una medida por otra** —las dos columnas van completas y divide quien lee— y **nada se ajusta por cobertura**; **no hay `ingestedAt` único en la raíz**, hay uno por medida. La credibilidad que viaja hoy es *cuándo leímos el origen*; *cuándo cambió el origen* está en `catalog` y **no hay enlace ficha↔`DatasetRef`**: no se inventa (ADR-019 §10), y no es uno a uno —el presupuesto tiene una ficha por ejercicio—.

## Contexto operativo (máquina de desarrollo)

- Windows 10 con PowerShell 5.1. Usar `.\mvnw.cmd` (nunca `mvn` global). En PowerShell 5.1 no existen `&&` ni `||`: encadenar con `;` o `if ($?) { ... }`.
- La herramienta Bash de Claude Code recibe el PATH de Windows con separadores `;` y no encuentra ningún binario. Si se usa, anteponer: `export PATH="/c/Program Files/Git/usr/bin:/c/Program Files/Git/cmd:/c/Program Files/Docker/Docker/resources/bin:/c/Program Files/Java/jdk-21.0.10/bin:/c/WINDOWS/system32:$PATH"`. Por defecto, usar PowerShell.
- `JAVA_HOME` apunta al JDK 21 (lo usa el wrapper). El `java` del PATH es Java 8: `java -version` engaña; fiarse de `.\mvnw.cmd -v`.
- Docker Desktop debe estar arrancado antes de `.\mvnw.cmd verify` (Testcontainers) y de `.\mvnw.cmd spring-boot:run` (Docker Compose). Comprobar con `docker info`; se puede arrancar con `Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"` y esperar.
- El puerto 8080 suele estar ocupado por un contenedor phpMyAdmin de otro proyecto: arrancar la app con `"-Dspring-boot.run.arguments=--server.port=8085"`. Para pararla, matar el proceso Java que escucha en el puerto y `docker compose -f compose.yaml stop`.
- Los commits con mensaje multilínea se hacen desde la herramienta Bash (`git commit -F - <<'MSG' … MSG` con el PATH de arriba); en PowerShell 5.1 los heredocs `<<` no existen y las here-strings fallan con `git commit -F -`.
- Base de datos: PostgreSQL con PostGIS, imagen `postgis/postgis:17-3.5` tanto en `compose.yaml` como en Testcontainers.
- No hay `spring` CLI ni `jq`. Hay `curl.exe`, `tar`, Python 3.12 (en `%LOCALAPPDATA%\Programs\Python\Python312`, no en el PATH de la herramienta Bash) y Node 24 con npm 11.
- CLI de Railway instalada con npm (`npm install -g @railway/cli@latest`; v5.49.5 el 2026-09-08), no con el `curl … | sh` que publica Railway: ese patrón lo bloquea el clasificador de permisos, y npm es además la vía de la regla 15. El MCP remoto de Railway se autentica con la sesión de la CLI, pero **una sesión válida no basta**: el 2026-09-08, con `railway whoami` correcto, el MCP seguía fallando con `CONNECTION_CLOSED` (queda pendiente reiniciar Claude Code, `ESTADO.md` §6). No bloquea nada: **la CLI cubre todo**, incluida la API pública.
- **La CLI de Railway devuelve 255 en órdenes que funcionan**: `railway status` (no hay servicio enlazado en la carpeta) y `railway metrics --service observatorio` imprimen su salida y salen con 255. Fiarse de la salida, no del código.
- **`railway api` es la salida para lo que la CLI no cubre** (así se activaron y verificaron las copias, regla 28). Dos trampas: `railway api search <término>` y `describe <tipo>` antes de escribir una consulta, porque los nombres de campo no se adivinan (`retentionSeconds`, no `retentionDays`); y en PowerShell **las comillas dobles del documento GraphQL no sobreviven** al paso al ejecutable, así que los identificadores nunca se escriben dentro de la consulta: van en `--raw-var clave=valor` o, si son listas o enumerados, en `--variables "@fichero.json"`.
- **`railway config` (IaC) en Windows**: el SDK comprueba la versión de la CLI ejecutando `process.env._` con `execFileSync`, que no puede lanzar ni el `.cmd` ni el shim de Git Bash; falla con «requires Railway CLI 5.42.1 or newer» aunque la instalada sea más nueva. Antes de `plan`/`apply`, en PowerShell: `$env:_ = "$env:APPDATA\npm\node_modules\@railway\cli\bin\railway.exe"`. Desde la herramienta Bash no funciona; usar PowerShell.
- Ficheros de texto en UTF-8 sin BOM (`Out-File`/`Set-Content` de PowerShell añaden BOM o usan ANSI: evitar para escribir fuentes).
- La herramienta Bash tiene un tope de longitud de comando: un heredoc de ~30 KB falla con `ENAMETOOLONG` y uno de ~9 KB se truncó en silencio. Los ficheros largos y los scripts se escriben con la herramienta Write (scripts en el scratchpad y `python script.py`); los comandos Bash se mantienen cortos. Un comando en segundo plano que termina en `| grep` devuelve exit 0 aunque Maven falle: redirigir a un log y buscar `BUILD SUCCESS`.
- Consultas SQL a la base de datos de Compose: `docker exec -i zaragoza-observatorio-postgres-1 psql -U observatorio -d observatorio < fichero.sql` (desde Git Bash, `docker exec … -f /tmp/x.sql` falla porque convierte la ruta a Windows).
